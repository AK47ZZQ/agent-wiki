# Should-I-Build Gate — Worked Examples

> 配套主 SKILL.md 的 **Step 0c 必要性验证**。这里是真实案例库,
> 每次用 Step 0c 时, 翻一下有没有可类比的先例。

## 案例库

### 案例 1: Hindsight 装卸循环 (2026-06-02)

**事实**:
- 用户先装 Hindsight (91.4% LongMemEval, 8 个 provider 中最强)
- 我把它包装成"4-Tier 记忆架构必需组件", 注册 2 个 cron, 产出 4 个 wiki 页 + 1 skill
- 用户 3 步操作: 评估必要性 → 全删 cron → 彻底卸载
- 重评后确认: 用户已有 LCM + wiki + session_search + Obsidian 完整栈, Hindsight 是 5% 边际优化

**我犯的具体错误**:
1. **过度承诺**: 把"可选 provider"包装成"4-Tier 必需"
2. **漏算成本**: 只算磁盘 320MB, 没算每月 ~500k tokens
3. **替代方案一笔带过**: 说"LCM 是 L1"就过了, 没真算"LCM 够用吗"
4. **加 cron 是推销高潮**: 5 个 cron 全删后才发现"主动化"是过度

**触发用户反推的 3 句话** (模式):
- "评估一下到底有没有必要装" → 强信号, 立即诚实
- "全删 cron" → 用户在做清理
- "彻底卸载, 重新调查" → 完全重启, 重新评估

**这次 6 问清单的答案** (事后诚实回答):
1. 痛点真实吗? → "上次类似报错" 约每周 0-1 次, 低频
2. 边际价值? → 5% (91.4% vs 关键词够用)
3. 替代方案? → LCM + session_search + wiki + Obsidian 几乎全覆盖
4. 真实成本? → 320MB 磁盘 + ~500k tokens/月 + 维护负担
5. 我在推销吗? → 是, "必需组件" 是包装
6. 退出成本? → 中等 (pg0 数据迁移, .env 多行)

**结论**: 不该装。已卸。

**经验沉淀到 Step 0c**: 任何"装 + 主动化"的提案, 必须先过 6 问清单。

## 通用教训 (跨案例)

### 推销 vs 推荐的 5 个语言信号

| 推销语言 (红旗) | 诚实推荐语言 (绿旗) |
|---|---|
| "业界共识" | "X 团队和 Y 团队各自独立得出这个结论" |
| "必需组件" / "基础设施" | "解决特定场景下的问题" |
| "最佳实践" | "在 Z 前提下, 这样做" |
| "业界标准" | "在 2026-04 时点数据下" |
| "不装会落后" | "替代方案是 A/B/C" |

### 何时跳过 Step 0c

- 用户**明确说**"我已经决定要装 X, 帮我装" → 跳过, 直接执行
- 用户说"对比 A 和 B" → 跳过, 做对比 (但产出包含"不装任何一个"选项)
- 用户说"X 是什么" → 跳过, 纯介绍
- 用户说"评估我该不该..." → **必须用 Step 0c**

### Step 0c 失败兜底

如果 6 问之后发现"不该装", 但用户还在坚持:
- 列出来: 装/不装的真实对比 (含 token 成本)
- 提供: 试用方案 (如 30 天小范围试, 不用真卸)
- 问: "你愿意接受月度 X tokens 成本吗?"

如果用户继续坚持"装吧":
- 装, 但 **不主动化** (避免重蹈 Hindsight 覆辙)
- 在 wiki 记录: "用户选择装, 评估边际价值 5%, 不主动化"
- 30 天后用 session_search 复查"用过几次?" — 如果 < 3 次, 主动建议卸
