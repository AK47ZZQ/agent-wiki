## 阶段 5: 重新探勘 + 实际部署 (2026-06-03)

**触发信号（用户原话）**：
- "先彻底卸载再重新探勘"
- "按照官方推荐的hindsight setup进行安装"
- "ai-harness-exploration 继续探索hindsight for Hermes"

**Agent 做的事**：
- 用 ai-harness-exploration 客观分析（不带预设）
- 读 Hindsight 官方文档：发现 native provider（旧 pip 已弃用）
- 实际本地部署：pip install hindsight-api (0.6.1) + 本地 server
- 配 Hermes config.json (不是 .env)
- 实测 retain→recall→reflect 完整链路
- 设计 handoff v1 防死循环（4 机制：限频/去重/幂等/人工触发）

**用户反应**：
- "已重启" → 然后 B 路径
- "ABD" → 3 个测试通过
- "删除 cron" → 主动要求零自动化

**关键学习**：
1. **第 2 轮"官方文档" + 实际部署是真正的"必要性验证"**——不上手不知道真价值
2. **handoff v1 设计是 Hindsight 案例的"成熟产物"**：
   - 不靠 cron（用户偏好）
   - 限频 3/天（避免烧 token）
   - 显式触发（避免自动）
3. **实测发现的隐藏知识**：
   - Hindsight v0.6.1 内存泄漏（GitHub Issue #996）—— 重要风险
   - 3 types vs 4 networks 的差异
   - 跨语言 query 通过 reranker 工作
   - Hermes 0.15.2 hybrid prefetch 实际未触发
4. **装后的"风险监控"是诚实评估的延续**：
   - 658 MB / 41 min → 长期跑必然 OOM
   - 需要每周手动重启

## "诚实的诚实评估" 8 问 (v2)

比原 6 问更严格：

```
□ 1. 痛点真实吗？
   用户的实际工作流里这个痛点多久出现一次？(低频=不必要)

□ 2. 边际价值多少？
   装上后比现状好在哪里？是"5% 增量优化"还是"不可替代"？

□ 3. 替代方案是什么？
   现有栈里有什么已经能覆盖？
   答案如果是"完全覆盖"→ 装 = 0 价值

□ 4. 真实成本是多少？
   不要只看"装一次多少磁盘"——要算"每月多少 tokens/维护/认知负担"
   = 装成本 + 月成本 × 12 + 退出成本

□ 5. 我在推销吗？
   检查自己的语气: 是"诚实推荐"还是"找理由证明它好"?
   红旗语言: "业界共识" / "必需" / "最佳实践"
   如果包装 → 立即停

□ 6. 退出成本多大？
   如果半年后想卸, 能卸干净吗?
   退出成本高 = 装的时候更要谨慎
   评估"如果 Hindsight 厂商 1 年后倒闭"怎么办

□ 7. 真实需求是什么？ (v2 新增)
   用户实际想要的是不是 Hindsight？或其实想要"升级 LCM"或"清理 4-Tier"?
   Hindsight 案例 2.0 揭示: 用户真实需求是"升级 LCM"而非"装 Hindsight"

□ 8. 第 2 轮探勘的时机 (v2 新增)
   是不是应该先卸了再评估？→ Hindsight 案例证明: 上手才知道真价值
   但卸的前提: 保留 .bak (退出成本低)
   = "装 + 测 + 卸"循环是正常的（用户预算内）
```

## 关键心法 (用 Hermes 偏好语言)

1. **"先卸了再调查"** 不是撤退 — 是诚实的科学方法
2. **退出成本低 = 装的前置条件** — 全部 .bak 备份是用户友好
3. **"上手才知道"** — 6 问清单是"该不该装"，不是"会不会用"——两者分开
4. **"已重启" 不等于 "同意"** — 简短回复可能是敷衍
5. **agent 推销的元信号**: "业界共识" / "必需" / "值得拥有" → 立即重评
6. **3 类推销模式**:
   - 推工具 (Hindsight) — 易反弹
   - 推自动化 (cron) — **最容易反弹** (烧 token 不可见)
   - 推架构 (4-Tier) — 难反弹（不烧 token）
7. **反弹的合理预期**: 推自动化的反弹 = 100% (用户偏好)
8. **"诚实" ≠ "什么都不推"** — 推 Hindsight OK，但**不推 cron**（自动化有边界）
