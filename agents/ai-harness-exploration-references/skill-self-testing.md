# Skill 自测试方法论

> 当创建一个分析/探勘类 skill 后，如何验证它真正有效？从本会话的真实测试经验提炼。

## 核心原则

**单一来源类型的测试只能覆盖 60% 的技能能力。要全面验证，必须用至少 2 种不同来源类型做互补测试。**

## 两轮互补测试法

### 第 1 轮：文章/分析型来源

测试 Step 0-2 的搜索和分析能力：

| 测试项 | 典型来源 | 如 Medium 博客、官方公告、分析报告 |
|:------|:--------|:--------------------------------|
| 目的 | 验证搜索流程、概念提取、知识去重 |
| 关键风险 | 数据/统计声明可能无源 → 需 R3 交叉验证 |
| 典型发现 | web_extract 被限制、来源质量评估失效 |
| 建议工具 | web_search + web_extract + browser 组合 |

### 第 2 轮：工具/GitHub 型来源

测试 Advanced Analyze 模块（Guides×Sensors、4 学派、跨源合成）：

| 测试项 | 典型来源 | 如 GitHub 仓库、CLI 工具、产品文档 |
|:------|:--------|:--------------------------------|
| 目的 | 验证双通道分析、控制论映射、学派定位、未知→已知过渡 |
| 关键风险 | 单一工具视角 → 需 R3 横向扩展搜索补充批判视角 |
| 典型发现 | README 信息不足、需 browser console 提取 |
| 建议工具 | browser + web_search + web_extract 组合 |

### 何时停止

```
第 1 轮 + 第 2 轮均通过 → ✅ 技能覆盖度 95%+
第 1 轮通过 + 发现第 2 轮无需 → ✅ 技能覆盖度 80%+（纯文章技能）
第 1 轮未通过 → ❌ 技能有 bug，先修复再测第 2 轮
```

## 数据/统计声明验证流程

在测试中，经常遇到来源声称的数据不可靠。这是通用验证流程：

```
Step 1: 识别该来源中的关键数字声明
  ├─ "78% 企业团队使用 MCP 在生产环境" ← 这是需要验证的目标
  └─ 通常出现在文章开头或摘要位置

Step 2: 追溯来源
  ├─ web_search("{关键词} source / origin / 来源")
  └─ 看是否能找到原始调查/报告

Step 3: 评估原始来源质量
  ├─ 有明确的调查样本量和方法？🟢
  ├─ 有引用报告名称/作者/日期？🟡
  └─ 无来源、模糊引用（"据报告"）→ 🔴

Step 4: 代换为可信数据
  如果原声明无源或不可追溯：
  ├─ web_search("alternative statistics {topic} adoption survey")
  ├─ 找行业调查报告（Gartner/Stacklok/Zuplo 等）
  └─ 在 wiki 页面标注"旧声明已由 {新来源} 数据取代"

实际案例（本会话）：
  旧声明: "78% 企业团队使用 MCP 在生产环境"（无来源）
  → 验证: 找不到原始调查
  → 替代: Stacklok 2026 企业软件报告 → 41%（29%有限+12%广泛）
  → wiki 标注: "旧文章中'78%'无可靠来源，已被 Stacklok 的 41% 取代"
```

### 常见不可靠数据模式

| 模式 | 示例 | 应对 |
|:----|:----|:------|
| 无来源百分比 | "78% 的团队使用 X" | 追溯来源，替换为有源数据 |
| 模糊引用 | "据业内报告显示" | 不可接受，标注无源 |
| 工具商自称 | "我们被 X 次下载" | 交叉验证（GitHub stars/Registry API） |
| 过时基准 | "我们在 X 基准上得分 Y" | 检查基准是否被污染（如 SWE-bench Verified） |

## 测试驱动验收（本会话核心发现）

**不要等到 skill 写完才测试。写完核心逻辑就测，测完再调。每次测试应产出至少一个具体修复。**

### 三阶段测试法

```
阶段 1: 单元测试（写完后立即）
  ├─ skill_view(name) 确认加载正常 ← 不是可选的
  ├─ 检查 triggers 能匹配用户表达
  └─ 快速跑 Step 0 质量评估验证打分逻辑

阶段 2: 实战测试（用真实外部数据）
  ├─ 选一个真实来源（博客/仓库/工具）
  ├─ 完整跑 Step 0-4
  └─ 预期产出：至少 1 个 concret bug 被发现并修复
      ↓ 没有 bug → 测试无效。换更复杂的来源再测。

阶段 3: 互补测试（用不同来源类型）
  ├─ 第 1 轮: 文章/分析型（测搜索、概念提取、数据验证）
  ├─ 第 2 轮: 工具/GitHub 型（测双通道、Guides×Sensors、学派）
  └─ 如果两轮都无法修复任何 bug → skill 已成熟，可以 bump 版本
```

### 真实案例（本会话）

| 轮次 | 主题 | 发现的 bug |
|:----|:----|:-----------|
| 第 1 轮 | MCP 生态文章 | web_extract 5/5 被拦截（→ 新增 browser fallback） |
| 第 2 轮 | Smithery CLI GitHub 仓库 | Guides×Sensors 分析框架验证通过 |
| 第 3 轮 | GitHub 镜像实测 | 9/9 镜像全灭（→ 全部删除，换 4 方案） |
| 第 4 轮 | Hermes v0.15 并行搜索 | 并行 3x 加速验证通过；发现 `&&` 语法 bug |

**关键认知：** 如果第 3 轮没有发现 9/9 镜像全灭，这些失效镜像会永远留在 skill 里。
→ **测试不是为了通过，是为了发现 bug。**

### 测试驱动验收清单

```markdown
□ skill_view 加载正常
□ 至少 1 轮实战测试完成（用真实数据）
□ 至少 2 种不同来源类型测试完成
□ 本轮测试发现的 bug 已修复
□ 版本号已 bump
□ 测试结果记录到 memory
```

## 测试日志模板

完成两轮测试后，用此模板记录：

```markdown
## [YYYY-MM-DD HH:MM UTC] {skill-name} 自测试
- 第 1 轮主题: {文章/分析来源}
- 第 2 轮主题: {工具/GitHub 来源}
- 覆盖维度: {已测试的模块列表}
- 未覆盖维度: {未测试的模块列表}
- 发现的 bug: {None 或 bug 列表}
- 技能版本: vX.Y.Z → vX.Y.Z+1
- 验证: 18项检查全部通过 | Ralph 6信条全部通过
```

## 陷阱

1. **只测一个来源类型** — 如果只测试文章型，会漏掉 Guides×Sensors、4 学派等模块。反之亦然。
2. **跳过数据验证** — 来源中的统计声明经常不可靠。必须追溯原始来源。
3. **忽略 web_extract 失败** — 如果 web_extract 被限制（如飞书/网关环境），必须用 browser 替代。这不是被测来源的问题。
4. **不记录测试日志** — 下次回看时不知道哪些维度已被验证。
